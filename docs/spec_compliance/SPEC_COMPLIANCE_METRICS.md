# Metrics Spec Compliance

This document tracks how the Ruby `metrics_api`, `metrics_sdk`, and `exporter/otlp-metrics` gems
align with the [OpenTelemetry Metrics specification](https://github.com/open-telemetry/opentelemetry-specification/tree/main/specification/metrics)
as of 2026-08-19. It supersedes the stale, unmerged draft on `add-metrics-compliance`
(`SPEC_COMPLIANCE.md`), which predates the current View/Aggregation/Exemplar/Exponential-Histogram
implementation and tracked GitHub PR numbers rather than code evidence.

## Methodology

- **Scope**: `specification/metrics/api.md`, `noop.md`, `sdk.md`, `data-model.md`,
  `sdk_exporters/otlp.md`, `sdk_exporters/in-memory.md`, `sdk_exporters/stdout.md`.
  `supplementary-guidelines.md` was reviewed and contains no MUST/SHOULD statements (purely
  informative), so it contributes no rows.
- **Requirement level**: only MUST and SHOULD statements are tracked. MAY/optional-feature
  statements are out of scope unless they're explicitly tracked in the org-wide
  `spec-compliance-matrix.md`.
- **§ numbering**: self-assigned per document (`API-N`, `NOOP-N`, `SDK-N`, `DM-N`, `OTLP-N`,
  `INMEM-N`, `STDOUT-N`), grouped in the order the requirement appears in the spec doc. These are
  not spec line/section numbers — the spec docs use plain markdown headers, not numbered clauses.
- **Stability**: taken from each section's own `**Status**: [Stable]` / `[Development]` /
  `[Mixed]` marker in the spec doc. `api.md` and `noop.md` are `Stable` at the document level
  ("except where otherwise specified"); `sdk.md`'s document-level status is `[Mixed]`, meaning
  stability varies by section — most sections carry their own explicit marker, and any that don't
  are treated as `Stable (unmarked)` per the spec's general convention that Stable is the default
  and Development/Experimental status is called out explicitly. `data-model.md` and the
  `sdk_exporters/*.md` docs don't use per-section markers at all and are treated as
  `Stable (unmarked)` throughout. This lets the gap summary separate "missing Stable MUST"
  (spec-alignment risk now) from "missing Development feature" (still in flux upstream, lower
  urgency).
- **Status legend**: ✅ Full · ⚠️ Partial · ❌ Missing · N/A Not applicable to this implementation.
- Every citation below was read directly from the referenced file/line at the time this document
  was written; none are taken on faith from a summary.

## Summary of gaps

Every ❌/⚠️ row above, grouped by stability (Stable gaps first — these represent spec-alignment risk
*now*; Development gaps second — the upstream spec itself is still moving on these, so they're
lower urgency) and then roughly by blast radius (an entirely-missing interface vs. a narrower
behavioral deviation).

### Stable — missing entirely

- **`MetricProducer`** (SDK-60): no way to plug a third-party metric source into a `MetricReader` alongside SDK-collected data.
- **`Enabled()`** on synchronous instruments (API-24, SDK-44): no `enabled?`/`enabled` method exists anywhere, so instrumentation authors can't cheaply skip expensive measurement work.
- **`schema_url`** on `MeterProvider#meter` (API-5, NOOP-2): silently dropped if passed; a `since 1.4.0` MUST.
- **`ExplicitBucketBoundaries` advisory parameter** (API-12, SDK-42): Histogram creation has no way to hint bucket boundaries without a full `View`.
- **Data point `flags` / staleness marker** (DM-9): `NumberDataPoint`/`HistogramDataPoint` have no `flags` field at all; `ExponentialHistogramDataPoint` has one but it's hardcoded to `0`.
- **Case-insensitive instrument name-conflict detection** (SDK-37): two instruments differing only by name casing register as unrelated instruments instead of colliding as the spec's own worked example requires.
- **Redirect following** (OTLP-10): `handle_redirect` is a literal no-op; redirect responses are retried against the original URI, never the `Location` header.
- **Post-shutdown blocking** (SDK-56, OTLP-11): both the base `MetricReader#shutdown` and the OTLP `MetricsExporter#shutdown` set no effective guard — `collect`/`export` keep working after `shutdown` is called.

### Stable — partial / behavioral deviations

- **View `attribute_keys` is not an allow-list** (SDK-13): it merges extra literal key/value pairs onto measurements instead of filtering the attribute set down to the listed keys — this is the single biggest semantic gap in the View implementation, since it's not a missing feature so much as a different feature living under the same name. No exclude-list either.
- **View `meter_schema_url` selection criterion missing** (SDK-12).
- **View `description`/`exemplar_reservoir` stream-config overrides not supported** (SDK-13, SDK-53) — `exemplar_reservoir` can only be set at instrument-creation time, not per-View, contradicting the spec's stream-configuration list.
- **Views added after instrument creation don't retroactively apply** (SDK-6) — only `add_metric_reader` is retroactive; `add_view` isn't.
- **Duplicate-instrument-registration warning over-fires** (SDK-36) — warns on any name reuse, even when all identifying fields are actually identical (not a real conflict per the spec's own definition).
- **Instrument `unit`/`description` are validated when the spec says SHOULD NOT** (SDK-39/40), and `nil` isn't coerced to `''` as required.
- **Async callback registration/unregistration exists only in the SDK, not the base API/proxy layer** (API-17/18) — calling `register_callback` on a `Meter`/instrument obtained before the global SDK installs raises `NoMethodError` instead of behaving as a no-op.
- **Async instrument creation can't take zero callbacks** (API-15/16) — `callback:` is a required keyword, contradicting "variable number...including none."
- **`MetricReader#Collect` returns raw data, not a status** (SDK-55) — no success/failure/timeout signal.
- **No guard against registering one `MetricReader` on two `MeterProvider`s** (SDK-54).
- **Exponential-histogram exemplar reservoir sizing** (SDK-50) uses CPU-count instead of `min(20, max_buckets)`.
- **`ExemplarReservoir` implementations aren't internally thread-safe** (SDK-65) — safe only because the one caller happens to hold a lock; not a property of the reservoir classes themselves.
- **`OTEL_EXPORTER_OTLP_METRICS_DEFAULT_HISTOGRAM_AGGREGATION` env var unread** (OTLP-3) — switching to exponential-histogram-by-default requires a `View`, not an env var.
- **No explicit NaN/Infinity policy** (SDK-63) in any aggregation's `update` path.
- **Stdout exporter doesn't use the spec-recommended 10000ms default interval** (STDOUT-3).

### Development — missing entirely (upstream still in flux; lower urgency)

- **`MeterConfigurator` / `MeterConfig`** (SDK-4, SDK-8, SDK-35) — no way to disable a `Meter` or configure it dynamically.
- **`Attributes` advisory parameter** (API-13, SDK-43) — no way to hint recommended attribute keys without a `View`.
- **`Bind`** (API-25, SDK-45) — no bound-instrument API.
- **`view_matching_mode` / `composable` View merging** (SDK-7) — only "independent" mode exists (which is, correctly, the spec's own default).
- **`MetricFilter`** (SDK-61) — no per-metric/per-attribute filtering hook on `MetricReader`.
- **SDK self-observability** (SDK-66).
- **`maxExportBatchSize`** on the periodic reader (SDK-57) — every collected batch is sent as a single `Export` call, unconditionally.
- **Exponential histogram NaN/Inf handling** (SDK-21) — same underlying gap as SDK-63, called out separately because this section of the spec is still Development status.
- **Per-timeseries async cumulative start timestamps** (SDK-28) — uses a simplified first-write-wins timestamp rather than distinguishing "first series in first collection" from "first occurrence in a later collection."
